## 自动化适合重复验证稳定规则

**结论**：高频回归、规则明确且结果可判断的场景适合自动化。探索性测试和体验评估仍需要人工判断。

**易错点**：自动化不是把所有操作录制一遍。测试需要明确断言，否则“脚本跑完了”不代表行为正确。

## 单元、集成与端到端

**结论**：单元测试关注小范围逻辑，集成测试关注模块协作，端到端测试关注完整用户路径。越接近完整环境，通常越慢、故障来源越多。

**易错点**：不能只靠大量 UI 用例覆盖底层规则，也不能只用单元测试替代关键业务路径验证。

## 实践：Node.js 内置测试

保存以下内容为 `age.test.mjs`，在 Node.js 22 中运行 `node --test age.test.mjs`，无需安装测试库。

```js
import test from "node:test";
import assert from "node:assert/strict";

function isEligible(age) {
  return Number.isInteger(age) && age >= 18 && age <= 60;
}

test("accepts inclusive boundaries", () => {
  assert.equal(isEligible(18), true);
  assert.equal(isEligible(60), true);
});

test("rejects invalid ages", () => {
  for (const age of [17, 61, 18.5, "18", null]) {
    assert.equal(isEligible(age), false);
  }
});
```

**预期结果**：两个测试通过。可把边界判断临时改错，确认测试会失败，再恢复代码；这能检验断言是否真的覆盖了规则。

## 不稳定测试的常见来源

共享可变数据、依赖执行顺序、真实外部网络和固定延时都可能导致偶发失败。优先等待明确的状态条件，并隔离测试数据，而不是不断增加等待秒数。

## CI/CD 流水线自动化测试策略

**结论**：CI/CD 自动化测试应遵循测试分层原则：单元测试放在流水线最前端作为快速门禁，端到端测试按需执行（不每次提交），耗时的性能和安全测试安排在夜间构建，同时善用并行化减少流水线总耗时。

**测试分层执行策略**：

| 测试类型   | 执行频率              | 特点                         |
| ---------- | --------------------- | ---------------------------- |
| 单元测试   | 每次提交              | 快速、稳定，首选门禁         |
| 集成测试   | 每次提交或合并        | 速度较快，依赖少量外部服务   |
| 端到端测试 | 合并主分支 / 定时构建 | 耗时长、稳定性差，不全量执行 |
| 性能测试   | 夜间构建 / 发布前     | 耗时长，不阻塞日常开发       |
| 安全扫描   | 夜间构建 / 发布前     | 耗时长，周期性执行           |

**关键原则**：
1. **快速反馈**：单元测试最先执行，让开发者尽快发现基础问题。
2. **频率与成本匹配**：测试执行频率应与耗时和稳定性成反比。
3. **并行化**：将测试用例分片在多个执行器上并行运行，缩短流水线时间。
4. **非阻塞测试后置**：性能、安全等非即时反馈的测试从主流水线分离，放入定时任务。

**易错点**：
- 端到端测试不是每次提交都完整运行，否则流水线耗时过长且易产生不稳定的失败（flaky tests）。
- 并行化时需注意测试用例间无数据依赖或资源冲突，否则可能导致测试相互干扰。
- 夜间构建失败应触发告警并纳入质量度量，不能忽略“非阻塞”测试的结果。

## JUnit 与单元测试

**结论**：JUnit 是 Java 语言最核心的单元测试框架，主要用于编写和运行单元测试，验证单个类或方法的正确性。它不负责发送 HTTP 请求、建立 TCP 连接，也不是专门用于集成测试的框架（尽管可配合其他工具用于集成测试）。

**JUnit 核心特性**：
- 使用 `@Test` 注解标记测试方法。
- 提供丰富的断言方法（`assertEquals`、`assertTrue`、`assertNotNull` 等）。
- 支持测试生命周期管理：`@BeforeEach` / `@AfterEach`（每个测试方法前后执行）、`@BeforeAll` / `@AfterAll`（所有测试方法前后执行一次）。
- 支持参数化测试、超时控制、异常测试、测试套件等扩展功能。

**JUnit 版本简史**：
- JUnit 4：经典版本，注解命名如 `@Before`、`@After`、`@BeforeClass`、`@AfterClass`。
- JUnit 5（Jupiter）：当前主流版本，注解命名改为 `@BeforeEach`、`@AfterEach`、`@BeforeAll`、`@AfterAll`，并引入模块化架构（JUnit Platform + Jupiter + Vintage）。

**与其他测试类型的关系**：
- **单元测试**：JUnit 的主要应用场景，测试单个类/方法，隔离性强。
- **集成测试**：JUnit 可与其他工具（如 Spring Boot Test、TestContainers）配合执行集成测试，但这不是 JUnit 的本质定位。
- 在测试金字塔中，JUnit 是单元测试层的基石，有助于快速反馈和早期缺陷发现。

**易错点**：
- 不要将 JUnit 与 HTTP 测试工具（Postman、RestAssured）或 API 测试框架混淆。
- JUnit 本身只提供测试执行框架，真正的单元测试依赖开发人员编写的测试逻辑和断言。
- JUnit 5 与 JUnit 4 的注解名不同，迁移时需注意。

## 测试覆盖率与分支覆盖率

**结论**：分支覆盖率衡量控制流分支（如 if-else、switch）的真假路径是否都被测试执行到。它回答的是“每个判定结果是否都走过”，而不是“每行代码是否执行过”。

**原因与区别**：

- 行覆盖率统计被执行的代码行比例，分支覆盖率统计被执行的判定路径比例。
- 两者可能不一致：一行代码被执行，只说明该行进入过；若其中的 if 只走 true 分支，false 分支仍未被覆盖。
- 常见同类指标：函数覆盖率（函数是否被调用）、条件覆盖率（复合条件中每个子条件取值）、路径覆盖率（组合路径）。
- 等价类划分是测试用例设计方法，用于选择输入数据，不是覆盖率指标。

**易错点**：把行覆盖率当成分支覆盖率。高行覆盖率不保证高分支覆盖率，边界与异常分支常被遗漏。

**适用条件**：分支覆盖率适用于含条件判断的代码；对无分支的直线代码，其意义与行覆盖率接近。JaCoCo 等工具可同时输出行、分支等覆盖率数据。

## 测试驱动开发（TDD）

**结论**：TDD 的核心价值是以可验证的需求定义驱动代码设计。它要求先写测试，再用测试约束并引导实现。

**关键机制**：

- 红-绿-重构循环：先写一个失败的测试（红），用最小实现让它通过（绿），再在测试保护下重构设计。
- 测试在这里首先是一种需求表达方式：每个测试用例描述一条可验证的行为约束。
- 自动化回归测试套件、较高的覆盖率是 TDD 的常见副产品，不是它的核心目标。

**易错点**：

- 把 TDD 等同于“提高覆盖率”：覆盖率是结果，不是驱动力。
- 把 TDD 等同于“减少测试工作量”：TDD 通常增加前期投入，收益体现在设计质量与后期修改成本。
- 把 TDD 当成测试阶段的活动：它是开发方法，测试先行服务于设计与需求澄清。

**适用范围**：适合需求可被拆成可验证行为的场景；需求极不明确或探索性原型阶段需谨慎使用。
