HTTP 与接口测试

言羽2026/9/8大约 9 分钟软件测试HTTP接口测试

幂等性不是响应完全相同

结论：幂等描述多次相同请求对服务器产生的预期效果与一次相同。PUT 和 DELETE 在 HTTP 语义上是幂等的，POST 不保证幂等。

易错点：第一次 DELETE 返回 204，第二次返回 404，不一定违反幂等性；资源最终仍是不存在的。业务实现也可能没有正确遵循方法语义，需要实际验证。

401 与 403

结论：401 表示缺少有效的身份认证凭据，403 表示服务器理解请求但拒绝执行。实际 API 还可能为隐藏资源存在性而返回 404。

易错点：HTTP 200 只说明 HTTP 层的这次响应成功，仍需检查业务码、字段、权限与数据副作用。

接口断言的范围

  • 状态码、响应内容类型与结构是否符合契约。
  • 字段值、边界输入、缺失参数及错误提示是否正确。
  • 当前用户能否访问其他用户的数据，服务端是否实际鉴权。
  • 重复请求、超时重试和并发请求是否产生重复数据。

实践：观察响应头

curl -i --connect-timeout 5 --max-time 10 https://example.com

该命令可用于观察公开站点的响应结构，不是业务接口测试的替代品。练习真实 API 时使用授权的测试环境，不把令牌、Cookie 或真实个人信息写进笔记。

SQL 注入检测方法

结论：基于时间的盲注通过注入包含延时函数的 SQL 片段，通过响应时间差异判断注入是否存在。该方法适用于无错误回显、无查询结果输出的场景。

SQL 注入检测方法对比：

方法原理适用场景
基于错误注入触发数据库错误，从错误信息判断应用回显数据库错误信息
基于 UNION使用 UNION SELECT 拼接查询结果页面显示查询结果
基于布尔（内容）盲注注入条件判断，比较页面内容差异无错误回显，但有可观察的内容差异
基于时间盲注注入延时函数，比较响应时间差异无错误回显、无结果差异输出

常见延时函数：

  • MySQL：SLEEP(n)
  • PostgreSQL：pg_sleep(n)
  • SQL Server：WAITFOR DELAY '0:0:n'
  • Oracle：DBMS_LOCK.SLEEP(n)

测试要点：

  1. 先记录正常请求的响应时间作为基准。
  2. 注入延时 payload（如 ' OR IF(1=1, SLEEP(5), 0)--）。
  3. 若响应时间显著延长（超过网络波动范围），则可能存在基于时间的注入。
  4. 通过条件判断（如 IF(1=1, SLEEP(5), 0) 与 IF(1=2, SLEEP(5), 0)）进一步确认。

易错点：

  • 时间盲注的响应时间差异可能受网络波动影响，建议多次测试并设置合理阈值（如至少 3-5 秒）。
  • 延时 payload 语法需根据目标数据库类型调整（MySQL、Oracle、SQL Server 函数不同）。
  • 注意数据库连接超时、负载等因素可能干扰测试结果。

安全测试基础与越权测试

结论：安全测试应从需求阶段及早介入，检查认证授权、权限滥用、数据泄露等风险。设计阶段需评审安全方案，越权测试是安全测试的关键类型之一。安全测试不可忽略，尤其对于涉及敏感数据的系统。

安全测试核心原则：

  1. 安全左移：在需求、设计、编码阶段尽早识别和修复安全风险，降低修复成本。
  2. 分层防护：在多个层级（网络、应用、数据）实施安全控制，避免单一防线失效。
  3. 持续测试：在 CI/CD 中集成安全扫描和渗透测试，确保持续安全。

常见安全测试类型：

  • 认证测试：验证登录、会话管理、密码策略等是否安全。
  • 授权/越权测试：验证用户是否能访问其权限之外的资源。
    • 水平越权：用户 A 访问用户 B 的资源（如同级权限用户）。
    • 垂直越权：低权限用户执行高权限操作。
  • 输入验证测试：检测 SQL 注入、跨站脚本（XSS）、命令注入等。
  • 敏感数据测试：验证敏感数据（密码、支付信息）是否加密传输和存储。
  • 日志与审计测试：验证安全事件是否被正确记录和审计。

安全测试关键阶段：

  • 需求阶段：分析安全需求，识别威胁模型。
  • 设计阶段：检查安全方案（认证、授权、加密、审计）。
  • 编码阶段：进行代码安全扫描（SAST）。
  • 测试阶段：执行安全功能测试和渗透测试。
  • 运维阶段：持续监控和定期安全评估。

易错点：

  • 安全测试不是仅在测试阶段执行的工作，需全流程参与（安全左移）。
  • 越权测试与认证测试不同：认证测试验证“谁可以登录”，越权测试验证“登录后能做什么”。
  • 忽略安全测试可能导致合规风险（如 GDPR、PCI-DSS）和重大安全事故，不能因“功能优先”而忽视安全。

k6 性能测试协议支持

结论：k6 内置支持 HTTP/HTTPS、WebSocket 和 gRPC 协议，不内置支持 JMS（Java Message Service）。其他协议（如 Kafka、Redis、SQL）需通过 xk6 扩展机制实现。

内置支持的协议：

  • HTTP/HTTPS：k6 的核心协议，支持 RESTful API 性能测试，包括各种 HTTP 方法、请求头、Cookie、认证等。
  • WebSocket：通过 k6/ws 模块支持，可测试 WebSocket 连接建立、消息收发和连接关闭等场景。
  • gRPC：从 v0.29.0 开始通过 k6/net/grpc 模块支持，支持 unary 调用和流式调用（client streaming、server streaming、bidirectional streaming）。

不内置支持的协议：

  • JMS：Java 消息服务协议，通常由 JMeter 通过 JMS 采样器支持。k6 不提供内置 JMS 支持。
  • AMQP、MQTT 等：消息队列协议通常需要 xk6 扩展或使用其他工具。

扩展机制：

  • k6 提供 xk6 扩展机制，允许开发者编写 Go 扩展以支持自定义协议。
  • 常见扩展包括 Kafka、Redis、SQL 数据库驱动等，但需自行构建 k6 二进制文件。

易错点：

  • 不要将 k6 与 JMeter 的协议支持范围混淆——JMeter 更擅长传统 Java 协议（JMS、JDBC），k6 更擅长现代 Web/微服务协议。
  • k6 的 gRPC 支持从 v0.29.0 引入，早期版本不支持，使用时需确认 k6 版本。
  • 扩展协议需要额外构建，不直接包含在官方发布的 k6 二进制文件中。

k6 常用性能测试指标

结论：http_req_failed 是 k6 中衡量 HTTP 请求失败率的指标（状态码 ≥ 400 的请求占比），属于 Rate 类型。其他常用指标包括请求响应时间（http_req_duration）、请求总数（http_reqs）和最大虚拟用户数（vus_max）。

k6 关键性能指标：

指标名称类型含义
http_req_durationTrendHTTP 请求的总响应时间（含网络、服务器处理、接收等）
http_req_failedRate请求失败率（状态码 ≥ 400 的请求占全部请求的比例）
http_reqsCounter测试期间发出的 HTTP 请求总数
http_req_waitingTrend等待服务器响应的时间（TTFB，Time To First Byte）
http_req_sendingTrend发送请求数据所花费的时间
http_req_receivingTrend接收响应数据所花费的时间
iterationsCounter脚本迭代（VU 执行一轮脚本）的总次数
checksRate自定义 check 的通过率（检查点验证）
vusGauge当前活动的虚拟用户数
vus_maxGauge测试期间达到的最大虚拟用户数

Threshold 配置示例：

export const options = {
  thresholds: {
    http_req_failed: ['rate<0.01'],      // 失败率 < 1%
    http_req_duration: ['p(95)<500'],    // 95% 请求 < 500ms
    http_reqs: ['count>1000']            // 总请求数 > 1000
  }
};

易错点：

  • http_req_failed 的“失败”默认基于 HTTP 状态码 ≥ 400，不包含网络超时或连接错误（这些也会计入失败，但判定方式不同）。
  • http_req_duration 包括发送、等待和接收的总时间，衡量端到端的响应速度。
  • Rate 类型指标在 k6 中输出为比例（0~1），Threshold 中设置 rate<0.01 表示 1% 的失败率阈值。

性能测试类型与浸泡测试

结论：浸泡测试（Soak / Endurance Testing）用于在长时间（如 72 小时）持续施加预期正常负载下评估系统稳定性和资源使用情况，主要用于发现内存泄漏、资源耗尽和性能退化。它不同于压力测试、容量测试和短期负载测试。

性能测试类型对比：

测试类型负载特点持续时间主要目标
负载测试预期正常负载短到中期验证响应时间、吞吐量等指标
压力测试超负载/极端条件中短期找到崩溃点、验证恢复能力
容量测试递增负载中期确定最大处理能力，规划扩容
浸泡测试预期正常负载长时间（数小时至数天）发现资源泄漏、长时间稳定性
尖峰测试突发高负载短时验证突发流量下的稳定性

浸泡测试关注点：

  • 内存泄漏：内存使用量是否随运行时间持续增长且不释放。
  • 资源耗尽：连接池、线程池、文件句柄等是否逐渐耗尽。
  • 性能退化：响应时间、吞吐量是否随时间下降。
  • GC 行为：垃圾回收频率和耗时是否逐渐恶化。

与其他测试的关键区别：

  • 压力测试关注超负载下的崩溃点，浸泡测试关注正常负载下的长时间稳定性。
  • 负载测试通常是短期的，浸泡测试强调持续性。
  • 容量测试关注最大处理能力，不强调长时间运行。

易错点：

  • 浸泡测试的负载是预期的正常负载，而非超负载（后者属于压力测试）。
  • 浸泡测试的核心是“时间维度”，即使负载正常，长时间运行才可能暴露资源泄漏。
  • 浸泡测试通常与监控工具配合，观察资源趋势而非单点指标。
