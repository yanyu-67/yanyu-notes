测试用例设计

言羽2026/9/8大约 14 分钟软件测试用例设计边界值

等价类划分

结论：把预计采用相同处理方式的输入划为一类，选代表值验证。有效输入与无效输入都应考虑。

例子：年龄只接受 18 到 60 的整数，可先划分为小于 18、18 到 60、大于 60，并补充空值、小数和非数字输入。

易错点：数字范围之外的格式错误，不能只用一个超范围数字代替。不同无效原因可能触发不同处理路径。

边界值分析

对于闭区间 [18, 60]，可选取边界及其邻近值：

输入预期
17拒绝：低于下界
18、19接受
59、60接受
61拒绝：高于上界

易错点：边界包含与否必须从需求确认；日期、字符串长度和数组索引也存在边界。具体测试集合取决于采用的边界覆盖准则。

判定表与状态迁移

结论：多个条件组合决定动作时可用判定表；结果依赖历史状态时可用状态迁移。

例子：是否会员、是否达到金额门槛共同决定折扣，适合判定表；订单从待支付到已支付再到已取消，适合状态迁移。

易错点：不能只测合法迁移。已取消订单再次支付、重复取消等非法或重复请求也需要明确预期。

逻辑覆盖强度排序

结论：逻辑覆盖标准按覆盖强度由弱到强排序为：语句覆盖 → 判定覆盖 → 条件覆盖 → 判定/条件覆盖 → 条件组合覆盖 → 路径覆盖。其中路径覆盖最强，但实际中通常不可行；在常见选项中，条件组合覆盖最强。

各覆盖标准定义：

覆盖标准要求强度
语句覆盖每个可执行语句至少执行一次最弱
判定覆盖（分支覆盖）每个判断的 T/F 分支至少执行一次弱
条件覆盖每个条件的所有可能结果（T/F）至少出现一次中等
判定/条件覆盖同时满足判定覆盖和条件覆盖较强
条件组合覆盖每个判断中所有条件组合至少出现一次强
路径覆盖覆盖程序中所有可能的执行路径最强（通常不可行）

关键理解：

  • 覆盖强度越高，测试充分性越好，但测试用例数量也相应增多。
  • 路径覆盖理论上最强，但在存在循环时路径数可能无限，实际难以实现。
  • 在实际项目中，通常不会追求最高覆盖，而是根据风险和资源选择适当的覆盖标准。

易错点：

  • 条件覆盖不要求考虑条件组合，因此强度低于条件组合覆盖。
  • 判定/条件覆盖虽包含条件覆盖，但只要求每个条件真/假至少出现一次，不要求所有组合，所以强度低于条件组合覆盖。

边界值分析测试用例设计

结论：边界值分析要求对每个输入边界测试最小值（min）、最大值（max）及其邻近值（略小于 min、略大于 min、略小于 max、略大于 max）。对于有效范围 [1, 5000]，标准测试集应包含 0.99（或0）、1、2（或任一内部点）、4999、5000、5000.01（或5001）。

边界值测试点选取规则：

  • min-（略小）：略低于最小值的无效输入，用于检测下溢出边界处理。
  • min（最小值）：边界上的有效输入。
  • min+（略大）：略高于最小值的有效输入，用于排除仅 min 能通过的异常。
  • max-（略小）：略低于最大值的有效输入。
  • max（最大值）：边界上的有效输入。
  • max+（略大）：略高于最大值的无效输入，用于检测上溢出边界处理。

选择邻近值的精度原则：

  • 邻近值的选择应基于输入域的最小单位（如金额按分，取 0.01 差值）。
  • 对于整数范围，min- 可取 min-1，min+ 可取 min+1。
  • 对于小数范围，取最小精度单位（如金额取 0.01，则 min- 取 0.99）。

常见误区：

  • 只测试边界点本身（min、max），忽略邻近值——错过边界判断逻辑错误（如 <= 与 < 混淆）。
  • 选用的无效边界值离边界太远（如 -1 和 10000），不能敏感发现边界处理缺陷。
  • 遗漏 min+ 或 max- 有效边界内部点，削弱了边界邻近有效值的验证。

黑盒测试与白盒测试的设计依据

结论：黑盒测试依据程序外部功能（需求规格说明、功能说明）设计测试用例；白盒测试依据程序内部逻辑（代码结构、流程图）设计测试用例。

黑盒测试特点：

  • 关注点：程序的行为是否符合需求，输入与输出是否正确。
  • 设计依据：需求文档、功能规格说明、用户故事。
  • 测试方法：等价类划分、边界值分析、判定表、状态迁移、错误推测等。
  • 优点：从用户视角验证，适合系统测试、验收测试。
  • 缺点：无法覆盖代码内部路径，可能遗漏未实现功能的缺陷。

白盒测试特点：

  • 关注点：程序内部执行路径、逻辑覆盖、数据流。
  • 设计依据：源代码、流程图、控制流图。
  • 测试方法：语句覆盖、判定覆盖、条件覆盖、路径覆盖等。
  • 优点：能发现代码逻辑错误，测试充分性可量化（覆盖率）。
  • 缺点：成本高，难以验证需求符合性。

关键区分：

  • 黑盒测试不需要了解代码实现细节，测试人员不关心“程序怎么做的”。
  • 白盒测试必须查看源代码，基于内部结构设计用例。
  • 实际项目中两者互补，形成完整的测试策略。

逻辑覆盖强度排序

结论：逻辑覆盖标准按强度由弱到强排序为：语句覆盖 < 判定覆盖 < 条件覆盖 < 判定/条件覆盖 < 条件组合覆盖 < 路径覆盖。其中路径覆盖最强，条件组合覆盖次之。

各覆盖标准定义：

覆盖标准要求强度
语句覆盖每条可执行语句至少执行一次最弱
判定覆盖（分支覆盖）每个判定的 T/F 分支至少执行一次弱
条件覆盖每个条件的所有可能结果（T/F）至少出现一次中
判定/条件覆盖同时满足判定覆盖和条件覆盖中高
条件组合覆盖每个判定中所有条件组合至少出现一次高
路径覆盖覆盖程序中所有可能的执行路径最强

关键理解：

  • 路径覆盖理论上最强，但实际中通常不可行（循环导致路径数量无穷，如 while 循环的路径数等于循环次数上限+1）。
  • 条件组合覆盖虽强，但不要求覆盖所有路径。
  • 覆盖强度是测试充分性的参考指标，而非绝对目标——应根据项目风险选择适当的覆盖标准。

易错点：

  • 不要把“条件组合覆盖”误认为强于“路径覆盖”——路径覆盖要求最高，理论上强于所有其他覆盖标准。
  • 路径覆盖的“路径”指从程序入口到出口的完整执行路径，而非代码行数。
  • 实际项目中很少追求 100% 路径覆盖，通常选择条件组合或判定/条件覆盖作为折中方案。

决策表法的适用场景

结论：决策表法适用于测试依赖多个条件组合的业务规则（如折扣计算、保险报价、权限判定）。它能系统性地枚举所有条件组合及其预期结果，确保覆盖全面，避免遗漏。

决策表法 vs 其他方法：

方法适用场景不适用场景
等价类划分单个输入域的分类多条件组合的交互验证
边界值分析数值范围边界检测离散条件组合、状态转换
决策表多条件组合业务规则无组合逻辑的单一输入测试
状态转换图有限状态机、状态序列系统无状态转换的计算场景

决策表法优势：

  1. 系统化覆盖：枚举所有条件组合，减少遗漏。
  2. 发现规则冲突：可识别同一组合对应多个矛盾结果的问题。
  3. 与业务对齐：规则清晰，便于与业务方评审和确认。
  4. 支持混合类型输入：同时处理离散条件（如用户等级、是否首次下单）和连续值（订单金额范围）。

典型适用场景：

  • 电商促销/折扣计算
  • 贷款审批/保险报价规则
  • 权限/角色判定逻辑
  • 优惠券、积分、会员等级组合规则

易错点：

  • 决策表适用于“组合逻辑”而非“状态序列”——状态转换图用于状态流转测试，两者不要混淆。
  • 当条件组合较多时（如本例 36 种），可结合等价类划分压缩组合数，再构建决策表（如订单金额先划分为 <100、100-500、>500 三类）。

语句覆盖的定义与作用

结论：语句覆盖用于评估所有可执行代码行被运行的比率，是白盒测试中最基础的覆盖标准。它要求每条可执行语句至少被执行一次，其他覆盖类型（判定、条件、路径）则关注逻辑分支和组合。

语句覆盖核心要点：

  • 度量指标：已执行语句数 / 总可执行语句数（百分比）。
  • 目标：确保代码中的每一条语句至少运行一次。
  • 局限性：仅覆盖语句执行，不保证逻辑分支（判定覆盖）或条件组合（条件覆盖）。

语句覆盖与其他覆盖标准的区别：

覆盖类型评估对象强度
语句覆盖可执行语句的执行最弱
判定覆盖（分支覆盖）每个判定条件的真/假分支弱
条件覆盖每个逻辑条件的真/假结果中
判定/条件覆盖判定和条件的组合中高
条件组合覆盖条件的所有组合高
路径覆盖所有执行路径最强

实际应用：

  • 语句覆盖常作为最低测试通过标准（如要求 ≥ 80%）。
  • 高语句覆盖率不等同于高测试质量，需结合其他覆盖指标（如判定覆盖）确保充分性。
  • 在 CI/CD 中，语句覆盖通常通过代码覆盖率工具（JaCoCo、Cobertura 等）自动度量。

易错点：

  • 语句覆盖不关注决策点（if、switch、循环等），因此即使 100% 语句覆盖，仍可能遗漏条件分支错误。
  • 不要把语句覆盖与等价类划分（黑盒测试）混淆——前者是白盒测试，后者是黑盒测试。
  • 覆盖率工具输出的“行覆盖”通常等同于语句覆盖，但不同工具的统计口径（如空行、注释行）可能略有差异。

因果图法

结论：因果图法根据输入条件（因）与输出结果（果）之间的逻辑依赖关系设计测试用例，适合处理多个输入条件组合影响输出的场景。它通过因果图分析逻辑关系，再转换为判定表生成用例。

核心概念：

  • 因（Cause） ：输入条件或输入条件的组合。
  • 果（Effect） ：输出结果或状态变化。
  • 逻辑关系：与（AND）、或（OR）、非（NOT）等，以及互斥、包含等约束。
  • 转换流程：分析需求 → 绘制因果图 → 转换为判定表 → 生成测试用例。

适用场景：

  • 输入与输出之间存在明确的依赖关系（如“若输入 A 为真，则输出 B 为假”）。
  • 多个输入条件共同影响一个或多个输出结果。
  • 需要覆盖有效和无效的因果组合。

与其他方法对比：

方法设计依据特点
等价类划分输入域分类不关注输入输出逻辑关系
边界值分析输入边界不处理条件组合
判定表条件组合与动作与因果图互补，因果图常转判定表
因果图输入输出逻辑依赖系统化处理复杂因果关系
路径测试代码路径白盒测试，非黑盒设计

易错点：

  • 因果图与路径测试不同：前者是黑盒测试设计方法，后者是白盒测试。
  • 因果图不是独立生成用例的终点，通常需转换为判定表后再设计用例。
  • 因果图适合逻辑依赖复杂的场景，简单输入输出关系可直接用等价类或边界值。

输入框验证测试的覆盖维度

结论：输入框验证测试应覆盖空值、非法字符、超长输入、边界值等多个维度，结合等价类划分和边界值分析，同时考虑安全性（注入、XSS）和格式校验。

主要测试维度：

维度测试要点示例
空值完全为空、仅空格、Tab 字符不输入任何内容提交
非法字符特殊符号、Emoji、SQL 注入、XSS 脚本输入 ' OR 1=1--、<script>
长度最小值、最大值、最大值+1、超长输入限制 20 字符时输入 19/20/21 字符
边界值边界取值及邻近值长度 0、1、max-1、max、max+1
数据类型数字、字母、字母数字混合、格式数据邮箱、手机号、日期等格式校验
安全性注入攻击、越权、编码绕过URL 编码、Unicode 编码绕过
特殊输入大小写、前后空格、换行符首尾空格是否被 trim

设计方法结合：

  • 等价类划分：将输入分为有效等价类（符合规则）和无效等价类（不符合规则）。
  • 边界值分析：重点测试长度限制的最小值、最大值、max+1，以及数值范围的边界。
  • 错误推测：根据经验补充特殊字符、编码绕过等场景。

关键原则：

  • 输入验证需前后端双重校验：前端校验提升用户体验，后端校验保证安全（前端可被绕过）。
  • 安全测试需覆盖 SQL 注入、XSS、命令注入等常见攻击向量。
  • 测试用例设计应覆盖正常路径和异常路径，并明确预期结果。

易错点：

  • 只测正常输入和边界值，忽略非法字符和安全性测试。
  • 仅依赖前端校验，忽略后端二次校验（攻击者可绕过前端直接调用接口）。
  • 未考虑输入中的前后空格、换行符等隐式字符对校验结果的影响。

因果图法

结论：因果图用于处理输入条件（因）与输出结果（果）之间存在明确逻辑对应关系的测试场景，特别适合多个条件组合决定输出的情况。

原因与机制：

  • “因”是输入条件，“果”是输出结果，因果图用逻辑关系（与、或、非）连接两者。
  • 先画出条件与结果的逻辑图，再把图转换为判定表或测试用例，确保覆盖各种条件组合。
  • 与判定表关系密切：因果图偏重逻辑建模，判定表偏重列出条件组合与动作，常配合使用。

与其他方法的分工：

  • 边界值分析针对数值范围的边界。
  • 等价类划分区分有效与无效输入，但不擅长处理多条件逻辑组合。
  • 错误推测法依赖经验，系统性弱，难以保证覆盖完整。

适用条件：需求中存在明确的 if-then 规则、多个输入条件共同决定输出时使用。条件之间逻辑简单或输出不受条件组合影响时，用等价类或边界值更直接。
